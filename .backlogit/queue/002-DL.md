# D-3: classify-close-path is truly read-only - no report write before the verdict returns

## Problem Frame

<!-- BEGIN:problem-frame -->
Plan revision 13 section 3.4.3 (B) states the new read-only mode classify-close-path "writes only its own additive report, exactly as mode detect-mixed-role already does", and section 3.4.3 (C) states the mode "returns, AND RECORDS AT .backlogit/reconcile/{shipment_id}-classify-close-path-{timestamp}.md", the five result fields. Frozen IV-1 requires the close path to be classified BEFORE ANY MUTATION, and frozen IV-5 requires the TDD harness to PROVE that refusal paths perform ZERO MUTATION. A report file written into the workspace during classification IS a workspace mutation and IS observable in any honest pre/post state comparison. The tension is therefore real and not merely rhetorical: under the behavioral harness adopted in the companion decision for stash E47FFCE7, a classification that writes a file before returning its verdict makes the zero-mutation assertion either FALSE or forces the harness to carve an exemption whose boundary is undefined - precisely the ambiguity that makes an IV-5 assertion unfalsifiable. The residual disposition of 2026-09-14 classified this as the finding "nearest to a category-(c) truly unresolved implementation blocker". Source refs: stash CE28BFA3, PR #54 (merged f7112e0), thread PRRT_kwDOTPuhps6irrge, shipment 021-S, feature 022-F, task 022.001-T, invariants IV-1 and IV-5 (plan section 12.1), plan sections 3.4.3 (B) and 3.4.3 (C).
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
OPTION 1 (REJECTED) - Keep the mandated report write and define it as PERMITTED TELEMETRY excluded from the zero-mutation guarantee. Matches the detect-mixed-role precedent and the frozen plan text, and needs no design change. REJECTED: it requires the IV-5 harness to carve a path-shaped exemption out of its own zero-mutation assertion. Once the assertion tolerates "mutations that are only reports", the assertion no longer distinguishes a report write from any other unintended write under the same directory, and IV-5 becomes unfalsifiable at exactly the point it matters most - the refusal path. It also weakens IV-1's plain reading ("before ANY mutation") by carving an exception into a FROZEN invariant, which section 12.1's Blocking rule forbids.
OPTION 2 (REJECTED) - Keep the write but guard it behind a flag that the harness disables. REJECTED as PRIMARY: it makes the assertion hold only in a configuration the production path does not use, so the harness proves zero mutation for a mode that is not the mode Ship actually invokes. Retained only as the narrow read-only-mode suppression clause inside Option 3.
OPTION 3 (ADOPTED, ROOT-SAFE) - CLASSIFICATION IS TRULY READ-ONLY. classify-close-path performs NO workspace or backlog mutation of any kind before returning its verdict. All five result fields are returned through the invocation result as machine-consumable output. Any persistence is OPTIONAL, happens strictly AFTER the verdict has been returned, is OUTSIDE the zero-mutation / refusal assertion window, and is suppressed entirely under read-only invocation. The zero-mutation assertion then needs no exemption and no path carve-out: the pre/post delta on a refusal path is EMPTY, full stop.
OPTION 4 (REJECTED) - Open plan revision 14 to rewrite sections 3.4.3 (B) and (C). REJECTED: revision 13 is FROZEN by operator disposition, attempt 9 is NOT authorized, and section 12.1 already resolves plan-text-versus-invariant conflicts in favour of IV-1..IV-5 without an edit. A revision 14 would reopen a closed gate for no additional binding force.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
ADOPT OPTION 3 - CLASSIFY-CLOSE-PATH MUST BE TRULY READ-ONLY AND MUTATION-FREE. Exact semantics, binding on Ship: (1) mode classify-close-path MUST NOT create, write, append to, rename, or delete ANY file, and MUST NOT mutate any backlog record, status, lock, or index entry, at ANY point BEFORE it returns its verdict. This explicitly includes .backlogit/reconcile/{shipment_id}-classify-close-path-{timestamp}.md. (2) CLOSE_PATH_VERDICT, VERDICT_REASON, VERDICT_EVIDENCE, CLASSIFICATION_BINDING and CLASSIFIED_AT are returned as MACHINE-CONSUMABLE OUTPUT of the invocation result itself; the returned value, not any file, is the authoritative carrier, and the CLASSIFICATION_BINDING that safe-close revalidates is taken from the returned value. (3) Persistence of a classification report is OPTIONAL, NEVER a precondition of a valid verdict, and MUST occur only AFTER the verdict is returned and OUTSIDE the zero-mutation / refusal assertion window; a failure to persist MUST NOT change, invalidate or block the verdict. (4) When the mode is invoked in read-only assertion mode, optional persistence is DISABLED ENTIRELY. (5) No file-lock is acquired, consistent with the existing detect-mixed-role read-only precedent. NO PLAN REVISION 14 IS REQUIRED: section 12.1 already makes IV-1 and IV-5 GOVERN over any conflicting plan statement, so sections 3.4.3 (B) "writes only its own additive report" and 3.4.3 (C) "and records at ..." are SUPERSEDED for the classification-before-verdict window by IV-1/IV-5 and by this decision, with no edit to the frozen plan. Attempt 8 FAIL STANDS; no attempt 9; no new review history is opened.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
None blocking. Whether Ship implements optional post-verdict persistence AT ALL is left to implementation; the simplest conforming implementation omits it entirely and satisfies Z1-Z5 trivially. If omitted, the classification report becomes purely a returned-value artifact and the cascade report produced later by the cascade sub-procedure (plan section 9, sub-procedure step 5) remains the only on-disk record, which is unaffected by this decision because it is written after the destructive call and therefore outside the classification window.

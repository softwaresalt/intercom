STRAND A - STAGE ARTIFACT PERSISTENCE ROUTE EXECUTION. DEFERRED, BLOCKED, NO SHIPMENT.

WHY THIS FEATURE EXISTS. 018-F delivers the PROHIBITION half of the Stage default-branch policy gap: Stage may not commit on the default branch, may create chore/stage-{scope-slug}, and must pass a fail-closed Step 1.9 gate before any tracked mutation. It deliberately delivers NO persistence EXECUTION. Until this feature lands, a Stage session terminates at a named fail-closed handback (STAGE_ARTIFACTS_UNCOMMITTED) with bounded artifacts UNCOMMITTED on the Stage branch, and completion is OPERATOR-ONLY: only the operator may verify, commit the allowed Stage roots, push the side branch, open and approve a merge-commit staging PR, update the default branch and re-verify the manifest. The Orchestrator MUST HALT at that checkpoint and MUST NOT execute its Step 1.5 item 3 uncommitted/unpushed arm, whose sub-item 3(e) attempts a DIRECT PUSH TO the default branch and whose commit arm contradicts the Orchestrator's own installed orchestration-only Role statement. This feature replaces the operator-only sequence with a specified, executable one.

SCOPE (four tasks): 019.007-T handback record emission with concrete artifact paths; 019.008-T no-shipment terminal reachability (failures still HALT); 019.009-T the Stage artifact commit step with out-of-root path safety; 019.004-T Orchestrator Step 1.5 authorization, branch discovery and concrete post-merge verification. 019.004-T is where any Orchestrator authority would be DELIBERATED, SCOPED AND REVIEWED - it does not exist today and 018-F creates none.

NOT IN THIS FEATURE. The reusable mechanical enforcement platform - structure-aware direct-push detector, fixture corpus, go test -json event parsing, regeneration-resistant CI wiring, CODEOWNERS and divergence ledger - is STRAND B, feature 020-F. The two strands were separated on 2026-09-12 because the old 019-F mixed PERSISTENCE SEMANTICS with REUSABLE ENFORCEMENT INFRASTRUCTURE, which have different consumers, different blast radius and different review needs. Neither strand depends on the other: after the split each depends only on 018.008-T and its own internal chain.

NO LIVE SHIPMENT - THIS IS THE ENFORCEMENT, AND IT IS DELIBERATE (rev 18). The rev-17 readiness lock used shipment 018-S with status "blocked" plus a blocks edge to lock-token shipment 020-S. That construction was INVALID: backlogit's shipment status enum is exactly queued|active|shipped|abandoned, so "blocked" is not a valid shipment status at all - the generic "backlogit move" CLI accepted it only through a known defect (verified by execution: move <shipment> --status blocked exits 0 while move <shipment> --status shipped exits 9). There is NO safe valid queued-shipment readiness lock in current backlogit semantics unless a genuine predecessor shipment is actually intended to ship, and a queued shipment is by definition claimable. 018-S and lock token 020-S were therefore ARCHIVED with the official non-destructive "backlogit archive" operation, their blocks edges removed first, and nothing was deleted. A blocked FEATURE with blocked TASKS and NO shipment is the safe representation: Orchestrator Step 2 and Ship Step 0.5 both operate on shipments, and there is no shipment to select, claim, or mis-route. Verified: "backlogit queue view" lists 017-S as the only shipment in the workspace.

HOW STAGE RECONSTITUTES THIS FEATURE. Only after 021.001-T records a REVIEWED decision selecting a valid harness execution model, Stage (never Ship, never the Orchestrator) performs, in order: (1) restructure the feature into whatever shape that decision requires; (2) run impl-plan, plan-harden (REQUIRED - this feature is intrinsically complex) and plan-review on the resulting plan; (3) only then CREATE A FRESH SHIPMENT over the reviewed shape and move the member tasks to queued. Creating a shipment before step 2 is a P-006 violation. Members of an archived shipment remain freely re-assemblable into a new shipment (verified by execution), so archival cost no future capability.

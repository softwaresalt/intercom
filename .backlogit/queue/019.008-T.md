SCOPE - make the stage_outcome: no-shipment terminal REACHABLE in .github/agents/_stage.agent.md. As installed, two clauses make it unreachable, leaving the Orchestrator's entire second verification arm as dead prescription: Step 5.5 declares shipment assembly "MANDATORY - not optional" whenever the registry advertises features.shipments: true and calls ending without a shipment_id a P-005 violation; and Step 6's pre-summary gate says that if no shipment_id exists, HALT and go back to Step 5.5 - so Step 6, where the handback line lives, is never reached.

Make the NARROWEST change that fixes this:
(a) scope Step 5.5's mandatory rule to a harvest that PRODUCED ITEMS, preserving its existing guardrail sentence VERBATIM ("do not assemble a shipment if the harvest step produced no items or produced items with unresolved P-003 violations; halt and report before creating an empty shipment") - that sentence is exactly the discriminator between a VALID EMPTY harvest (terminates as no-shipment) and unresolved P-003 violations (still HALTS);
(b) require shipment_id in Step 6's pre-summary gate ONLY when stage_outcome is shipment; for no-shipment require instead the COMPLETE handback record plus an explicit terminal statement that there is nothing to route to Ship;
(c) the no-shipment summary MUST NOT direct the operator to Ship - with no shipment the correct handoff is NONE.

FAILURES STAY FAILURES - LOAD-BEARING CONSTRAINT: no-shipment is a SUCCESS terminal for a run that had nothing to ship. It is NEVER a re-label for failure. A P-003 lineage violation, a harvest that errored, and a harvest that produced items but could not form the required shipment ALL CONTINUE TO HALT exactly as they do today and MUST NOT be recorded as no-shipment. Without that constraint this edit would convert the pipeline's loudest failure mode into a silent success - strictly worse than the unreachable arm it fixes.

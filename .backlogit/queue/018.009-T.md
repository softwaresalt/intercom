Parent feature 018-F. Sub-epic B, plan section 6.3 of docs/plans/2026-09-11-intercom-go-stage-artifact-branch-pr-policy-gap-plan.md. Correct the OPERATIVE authorization surface in .github/agents/_stage.agent.md, which role-enforcement treats as the authoritative permission set at mutation time. (1) The Role Boundary Git row Allowed cell currently reads 'Commit backlog/planning artifacts on default or admin branch'. Narrow it to the dedicated Stage/admin artifact branch only. (2) In the SAME Allowed cell, ADD an explicit grant to create and check out that dedicated artifact branch (chore/stage-{shipment_id}, or chore/stage-{chore-slug} when no shipment is formed), mirroring the P-010 grant added by 018.008-T - without it, role enforcement fails closed on the very branch creation the corrected policy requires. (3) Add an actor note on the PR row recording that the Orchestrator (pipeline invocation) or the operator (direct invocation) - never Stage - pushes the branch and opens/merges the staging PR, so the corrected Git row does not imply a forbidden Stage action. The PR row is the ONE row exempted from the otherwise-unchanged requirement in AC-B3.3; its prohibition is unweakened.
(4) STEP 6 HANDBACK EMISSION: add to Stage's STEP 6 (Summary) session-output contract one required line emitting the STAGING HANDBACK RECORD the Orchestrator's Step 1 consumes (018.007-T, AC-B1.5): stage_branch, stage_base_commit, stage_head_commit, stage_outcome (shipment|no-shipment), stage_artifact_paths, and shipment_id when one was formed. Without it the Orchestrator's handback requirement has no producer and every pipeline run falls into the STAGING_HANDBACK_DEGRADED path. It transfers NO authority - emitting a branch name, a commit pair, and a file list is not pushing, opening, or merging anything.
(5) PATH AND COMMIT SHAPE IN THAT SAME LINE: stage_artifact_paths is a NON-EMPTY list of CONCRETE repository-relative FILE paths - the files Stage committed BETWEEN stage_base_commit AND stage_head_commit, NEVER directory prefixes and NEVER only the tip commit's files - and the line names the derivation Stage uses to produce them: git diff --name-only -z --diff-filter=d {stage_base_commit} {stage_head_commit} -- .backlogit/ docs/plans/ docs/decisions/ docs/memory/. Naming the producing command here is what makes the consumer's SET-EQUALITY check (018.007-T AC-B1.10) satisfiable by construction rather than by coincidence: two surfaces computing the same set from the same commit PAIR with the same command cannot disagree. Stage ECHOES stage_base_commit rather than inventing one - the Orchestrator's retained pre-invocation value is authoritative (AC-B1.5) - and the echo exists so a DIRECT Stage invocation, which no Orchestrator bracketed, still hands the operator a usable base.
(6) MAKE THE no-shipment TERMINAL OUTCOME REACHABLE. As installed, two clauses make stage_outcome: no-shipment unreachable, which leaves the Orchestrator's entire second verification arm as dead prescription: Step 5.5 declares shipment assembly 'MANDATORY - not optional' whenever the registry advertises features.shipments: true and calls ending without a shipment_id a P-005 violation; and Step 6's pre-summary verification gate says that if no shipment_id exists, HALT and go back to Step 5.5 - so the summary, where the AC-B3.5 handback line lives, is never reached. Make the NARROWEST change that fixes this: (a) scope Step 5.5's mandatory rule to a harvest that PRODUCED ITEMS, preserving its existing guardrail sentence VERBATIM ('do not assemble a shipment if the harvest step produced no items or produced items with unresolved P-003 violations; halt and report before creating an empty shipment'), which is exactly the discriminator between a VALID EMPTY harvest (terminates as no-shipment) and unresolved P-003 violations (still HALTS); (b) require shipment_id in Step 6's pre-summary gate ONLY when stage_outcome is shipment, and for no-shipment require instead the COMPLETE handback record plus an explicit terminal statement that there is nothing to route to Ship; (c) the no-shipment summary MUST NOT direct the operator to Ship - with no shipment the correct handoff is NONE, and the Orchestrator's Step 1.5 no-shipment arm is the terminal gate.
FAILURES STAY FAILURES - LOAD-BEARING: no-shipment is a SUCCESS terminal for a run that had nothing to ship. It is NEVER a re-label for failure. A P-003 lineage violation, a harvest that errored, and a harvest that produced items but could not form the required shipment ALL CONTINUE TO HALT exactly as they do today and MUST NOT be recorded as no-shipment. Without that constraint this edit would convert the pipeline's loudest failure mode into a silent success - a strictly worse defect than the unreachable arm it fixes.
SCOPE: items (4), (5) and (6) are the ONLY edits outside the Role Boundary table; no other section of _stage.agent.md is modified.

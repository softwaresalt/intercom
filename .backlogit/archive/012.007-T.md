Register entry for 5FE4A7BE in internal/pathsafe/root.go's package doc, carrying ITS OWN task-ID attribution and explicitly stating it is NOT a BF5DE670 item. Record BOTH directions. DARWIN (under-folding): the fold is Windows-only; darwin is a shipped target per scripts/targets.json (darwin/amd64 and darwin/arm64, verified) and is case-insensitive by default on APFS/HFS+. STATUS: accepted, FAIL-CLOSED - worst case is rejecting a legitimate path. Extending the fold to darwin was REJECTED because on a case-SENSITIVE APFS volume it would convert a rejection into an acceptance, i.e. fail-OPEN, which is backwards for a containment control. The darwin availability defect is labelled PLAUSIBLE/UNCONFIRMED pending a reproduction. WINDOWS (over-folding): the fold that is ALREADY ENABLED is itself a potential fail-open - NTFS supports per-directory case sensitivity (fsutil file setCaseSensitiveInfo; WSL enables it by default on directories it creates), so on such a root a symlink resolving to a case-variant sibling can be folded into acceptance - the exact construct rejected for darwin. TRIGGER: a workspace root on a case-sensitivity-enabled or WSL-created tree. NOTE: the originally proposed advisory macOS CI job was DROPPED after review - GitHub macOS runners use case-INSENSITIVE APFS by default so the job could not exercise the hazard, and it would have opened .github/workflows/ci.yml which is the surface of excluded entries F4F4A959 and F47DB9A9. 5FE4A7BE's own text authorizes these remedies with 'and/or', so this register entry discharges it.

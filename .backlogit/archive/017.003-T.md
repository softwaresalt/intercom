title: Make MAX_PATH threshold UTF-16 code-unit aware
updated_at: 2026-09-11T02:46:48.9337242Z
---

Make addLongPathPrefix's MAX_PATH threshold comparison UTF-16-code-unit-aware (internal/pathsafe/reparse_windows.go) instead of using UTF-8 byte length as a proxy for the count Windows actually measures.

Current: if len(path) < longPathThreshold where longPathThreshold = syscall.MAX_PATH (260). len() counts UTF-8 BYTES; Windows counts UTF-16 CODE UNITS.

Measured this cycle:
  200 x U+00E9 ('e-acute') -> 400 UTF-8 bytes, 200 UTF-16 units, 200 runes
  100 x U+1F600 (emoji)    -> 400 UTF-8 bytes, 200 UTF-16 units, 100 runes

UTF-8 byte length is ALWAYS >= UTF-16 code-unit count (1->1, 2->1, 3->1, 4->2). The existing proxy therefore fires AT OR BEFORE the true limit: it can produce a FALSE POSITIVE (prefixing a path that did not need it) but NEVER a false negative. THIS IS A PRECISION IMPROVEMENT, NOT A CORRECTNESS OR SECURITY DEFECT. Any framing of it as a vulnerability fix is an explicit anti-goal.

IMPLEMENTATION: use len(utf16.Encode([]rune(path))) or a plain or _, r := range path accumulator. The deliberation's original O2-c "non-allocating bespoke counter" was WITHDRAWN at plan review as gold-plating: addLongPathPrefix's only caller immediately calls syscall.UTF16PtrFromString (which allocates) and then two Win32 syscalls, so saving two small allocations buys nothing while adding bespoke infrastructure to a NON-NEGOTIABLE control. A rune count (O2-a) is REJECTED: a surrogate pair is 1 rune but 2 UTF-16 code units, so a rune count can UNDER-count and introduce the false negative the current code never has.

DEPENDS ON 017.002-T - COORDINATION, NOT REGRESSION-NET. 003 changes only the first (length) guard; a \\.\ device path of any length clears the length guard and is caught by the unchanged device/\\ guards regardless of byte-vs-code-unit counting, so 003 CANNOT regress the device-path property 002 locks. The real constraint is same-function / same-doc-comment merge coordination.

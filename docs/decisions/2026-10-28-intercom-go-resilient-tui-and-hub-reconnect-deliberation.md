## Problem Frame

Following the completion and post-merge closure of the `063-S..066-S` post-MVP hardening chain (`066-S` merged at `65780da0d83a53182a56460093b80cc132b5d945`, closure at `7617a00fc29660cac87dd8d67a177518e0d68ec2`), the operator selected **Capability Set 1: Resilient TUI & Hub Reconnect Experience** for execution in dark-factory mode (`DARK_MODE_ACTIVE`, P-017). Capability Set 1 comprises seven deferred-scope-expansion stash entries captured under P-021 C2 during `058-S`, `059-S`, `061-S`, and `065-S`:

1. **`1DCB6108`** (`high` / `feature`): Add hub in-place `Client.Rehydrate` (and bounded redial retry / re-dial on hub-dropped TUI client) so the TUI feed overflow reconnect no longer opens a no-TUI window that can auto-deny a pending permission (`UserNotAvailable`) and a transient redial failure does not permanently strand the always-approver TUI surface.
2. **`550437DB`** (`high` / `task`): Hub lifecycle wiring gaps for process wiring (7.2): `Hub.Run` ctx cancelled (`SIGINT`) before `Shutdown` stops hub immediately so step 0 returns `ErrStopped`; `Shutdown.Done` never closes if `Start` never called; failed-start cleanup semantics (`Abort` `ErrNotRunning`); `Hub.Run` does not join operator lane workers; operator action `Send`/`Abort` failures only logged (surfaces not told - needs protocol decision); no abort of pending permissions on aborted idle event.
3. **`E9223340`** (`medium` / `feature`): TUI hardening and wiring follow-ups: (a) `cmd` entrypoint wiring `tea.NewProgram` + `Feed` + `HubDialer` [already absorbed in `062-S`]; (b) live transcript entry cap and per-entry render cache ($O(N)$ per delta); (c) model-initiated re-hydrate when `Cursor` rejects a hydrate (stuck resync); (d) treat non-`Cf` invisible blank runes (`U+3164`, `U+2800`, `Co`) as hidden in `Sanitize` and blank-summary check; (e) indent permission summary to prevent spoofed kind/tool-call lines; (f) minimum on-screen delay before approve/deny keys; (g) prompt local echo, deadline countdown, display-width-aware prompt truncation, mouse scroll.
4. **`4AFE4DA4`** (`medium` / `task`): Shutdown/broadcast fidelity: stale (overflowed) clients never receive `server.shutdown` before close; write-pump drain only checks queue emptiness not write completion; empty-broadcast-set rule ignores queued pending connects (reconnect in flight) and observer-only remote surfaces keep requests pending to timeout; closed clients not swept before admission.
5. **`AEF57AF1`** (`low` / `bug`): Pre-existing hardening candidates found during `065-S` adversarial review: `internal/hub/shutdown.go` `drainAndCloseClients` treats the queue as empty once `writePump` dequeues the final `server.shutdown` frame while `Handler.Drain` can cancel before `writeFrame` completes (candidate cause of rare `TestE2EShutdown`/`SIGINT` flake: remote sees `server.shutdown` before `permission.resolved`); `internal/app/e2e_test.go` `shutdownScenario` drains the remote only after `Done` so `closeSocket` waits the 2 s grace; `App.Reissue`/`tuiReissue` discard `ctx`.
6. **`8769C9A0`** (`low` / `task`): Idle accounting and stop latency edge cases: hub `promptsPending` assumes one `turn.start` per accepted prompt (coalesced/mid-turn prompts or agent-initiated turns can stall `WaitIdle` to its bounded timeout); `recheckForce` can add up to another `StopTimeout` to `Stop` latency after a failed `Start`; hub `Force` budget vs adapter `StopTimeout` coupling documented not validated.
7. **`2C74C5FC`** (`low` / `task`): Hub residual hardening from `058-S` review cycles - (a) `publish` stub path applies a second fold error entry when caller already folded one; (b) `admitPending` counts unswept closed remotes toward the pending cap (sweep at intake start); (c) `publish` returns `(0,false)` without `markAllStale` if even the stub cannot be built; (d) fold `applyDelta` re-marshals at cap for tiny deltas (early return when truncated and add empty); (e) `tool.ended` name fold-vs-live parity; (f) drain stale remote buffer before rehydrate instead of dropping (H-5).

## Research Findings

### Compound Learnings Consulted

* `docs/compound/2026-10-20-process-wiring-credential-panel-and-approval-disarm.md`: Documents the single choke point for disarming armed permission approvals in `onKey` (every key other than `Enter` disarms before any early return), passing initial credentials at `tui.New` construction, and running the hub on a context never cancelled by `SIGINT` before shutdown step 6.
* `docs/compound/2026-10-20-tui-permission-modal-safety-and-linux-test-clock.md`: Documents pinning both `Config.Clock` and `Config.Now` in deterministic hub/TUI tests, keeping `syncModal` synchronized after every mutation of `m.pending`, keeping deny (`n`) available immediately at all times, and separating input fidelity (sent verbatim) from display sanitization (`Sanitize`).
* `docs/compound/2026-10-20-backlogit-cli-pitfalls-and-permission-outcome-lessons.md`: Documents atomic `PermissionOutcome` (`Deliver` vs `Revoke`), running `Agent.Stop` under `context.WithoutCancel` with a hard budget, and keeping delivery-uncertain failed `Send` calls counted in `promptsPending` so a late failure never consumes a later prompt's count.

### Codebase Inspection Findings (Baseline `066-S` / `65780da`)

1. **`2C74C5FC` (`internal/hub/fold.go` & `internal/hub/hub.go`)**:
   * **(a) Duplicate fold error entry on `publish` stub path**: In `internal/hub/hub.go:680-684`, when `publish(kind, payload)` falls back to the `ErrCodeFrameTooLarge` stub, it unconditionally calls `h.fold.ApplyError(ErrCodeFrameTooLarge, msgFrameTooBig)`. When `kind == KindError` (called from `handleDegraded`, `handleEvent` for an unmapped event, or our new operator-action-failure handler), the caller has already called `h.fold.ApplyError(...)`, so the stub path records a duplicate second error entry for the same event. Guarding `if kind != KindError { h.fold.ApplyError(ErrCodeFrameTooLarge, msgFrameTooBig) }` prevents the duplicate entry.
   * **(b) Unswept closed remotes in `admitPending` (also `4AFE4DA4(d)`)**: In `internal/hub/hub.go:920`, `intake` calls `h.admitPending(req)` without calling `h.sweep()`, so remote clients that already closed themselves still count toward `live+remote >= h.pendingLimit()` until `serviceHydrations` runs on the next iteration. Calling `h.sweep()` at the start of `intake` fixes both `2C74C5FC(b)` and `4AFE4DA4(d)`.
   * **(c) `publish` returning `(0, false)` without `markAllStale`**: In `internal/hub/hub.go:674-677`, if building even the error stub fails, `publish` returns `(0, false)` without calling `h.markAllStale()`. Because `handleEvent` / `handleDegraded` already mutated `h.fold` before calling `publish`, connected clients are out of sync with the fold unless `h.degradedSeq = h.seq` and `h.markAllStale()` are executed before returning `(0, false)`.
   * **(d) `Fold.applyDelta` re-marshalling at cap**: In `internal/hub/fold.go:193`, `if add == "" && !clipped { return }` is false whenever a streaming entry is already at `MaxEntryTextBytes` (`remaining == 0`) and a non-empty delta arrives (`add == ""`, `clipped == true`). Even when `cur.Truncated` is already `true`, `applyDelta` runs `f.replace(i, cur)`, re-marshalling the entire 16 KiB entry on every tiny delta. Changing the early return to `if add == "" && (cur.Truncated || !clipped) { return }` (after setting `f.lastDelta` and `f.anyTrunc`) avoids all redundant marshals once `cur.Truncated` is already set.
   * **(e) `tool.ended` name and truncation parity**: In `internal/hub/fold.go:212-225`, when `applyToolEnded` finds a matching `statusRunning` tool entry, it updates `cur.Status` but ignores `ev.ToolName` and its truncation flag `t2`, whereas `mapEvent` (`internal/hub/envelope.go:275-279`) always bounds `ev.ToolName` with `capIdent` and sets `Truncated: t1 || t2`. Bounding `name, t2 := f.identFlag(ev.ToolName)` up front in `applyToolEnded` and setting `if cur.Tool == "" && name != "" { cur.Tool = name }` and `cur.Truncated = cur.Truncated || t1 || t2` (alongside matching `if m.entries[i].Tool == "" && name != ""` and `m.entries[i].Truncated = m.entries[i].Truncated || p.Truncated` in `internal/tui/model.go` `applyToolEnded`) establishes full fold-vs-live parity.
   * **(f) Drain stale remote buffer on `rehydrate` instead of dropping**: In `internal/hub/hub.go:1099-1102`, `rehydrate(c)` drops `ClientRemote` if `trySend(c.send, f)` finds `c.send` full. Because `rehydrate(c)` is only called for clients marked stale by a hub-wide re-hydrate (`markAllStale` after `SignalDegraded` or an oversize frame stub, or explicit `Client.Rehydrate`), any frames in `c.send` are pre-hydrate frames superseded by the snapshot `f`. Removing the `if c.kind != ClientTUI` drop branch in `rehydrate(c)` so a full `c.send` is drained before sending `f` for both `ClientTUI` and `ClientRemote` (while normal `broadcast` continues to drop `ClientRemote` on overflow) preserves healthy remote clients across degraded-mode re-hydrations.

2. **`550437DB` & `8769C9A0` (`internal/hub` & `internal/agent/copilot`)**:
   * **Process wiring items already handled in `internal/app` (`062-S` / `065-S`)**: `internal/app/assemble.go:220` runs `Hub.Run` on a signal-independent `context.Background()` child cancelled only in `awaitHub()` after step 6; `Shutdown.agentStage` (`internal/hub/shutdown.go:205`) treats `agent.ErrNotRunning` and `agent.ErrStopped` from `Abort` as `noSession = true` (non-error); and `NewShutdown` spawns no goroutine until `Start` is called. We document these caller contracts explicitly in `internal/hub/hub.go` and `internal/hub/shutdown.go`.
   * **Joining operator lane workers in `Hub.Run` (`550437DB`)**: `runOperatorLanes(opsCtx)` in `internal/hub/operator.go:53` spawns two worker goroutines without a `sync.WaitGroup`, so `Hub.Run` can return and close `h.done` while a lane worker is still unwinding. Passing a `*sync.WaitGroup` (`lanesWG`) to `runOperatorLanes`, registering `defer lanesWG.Wait()` before `defer opsCancel()` in `Hub.Run` (so `opsCancel()` runs first and `lanesWG.Wait()` completes before `defer close(h.done)`), and adding `case <-ctx.Done():` to the `h.promptFailed` send select ensures deterministic worker join before `Hub.Done()` closes.
   * **Protocol decision for asynchronous operator `Send`/`Abort` failures (`550437DB`)**: Because `OpPrompt` and `OpAbortTurn` are authorized on the hub goroutine and handed to off-hub lane workers (design §4.1), `Client.Do` returns `ActionResult{Accepted: true}` as soon as the action is queued. When `Agent.Send` or `Agent.Abort` subsequently fails in `callAgent` (and `ctx.Err() == nil`, meaning the failure was not caused by shutdown lane cancellation), logging alone is invisible to remote WebSocket surfaces and to a local TUI whose stderr is discarded on a terminal. We decide to report non-shutdown lane call failures back to the hub select loop via a buffered `actionFailed chan string` channel; the hub goroutine (when `!h.closing`) folds `h.fold.ApplyError(ErrCodeOperatorActionFailed, msg)` and publishes `KindError` (`ErrorPayload{Code: ErrCodeOperatorActionFailed, Message: msg}`, with fixed sanitized messages `"operator prompt send failed"` and `"operator turn abort failed"`, without setting `degradedSeq` or `markAllStale`). Both the TUI and remote clients already render `KindError` entries in the transcript.
   * **Resolving pending permissions on aborted `agent.idle` (`550437DB`)**: Per design §3.1 SQ-a, `Session.Abort` in the Copilot SDK returns `nil` and emits an aborted idle event (`agent.Event{Kind: agent.KindIdle, Aborted: true}`) without unblocking an already-parked `PermissionHandlerFunc`. Furthermore, `h.ingress` and `h.asks` are independent channels (`internal/agent/agent.go`). When `handleEvent` receives `ev.Kind == agent.KindIdle && ev.Aborted`, it first drains any permission asks already queued in `h.asks` (registering or answering them `DecisionUnavailable` with `permReasonTurnAborted = "turn_aborted"`), then settles any `e.state == permDecided` entries via `h.settleDecided(e, permReasonTurnAborted)` (atomically revoking any unconsumed approval via `e.ask.Outcome.Revoke()`), and finally resolves every unresolved entry in `h.perm.unresolved()` to `agent.DecisionUnavailable` with `permReasonTurnAborted` via `h.decide`, immediately unblocking parked permission handlers and clearing the permission modal on all surfaces.
   * **Non-blocking `Adapter.recheckForce` and `ShutdownConfig.AdapterStopTimeout` validation (`8769C9A0`)**: In `internal/agent/copilot/adapter.go:676`, `recheckForce()` currently calls `a.forceStop()`, which starts a second full `StopTimeout` timer even though `Start`'s failure cleanup already waited `StopTimeout` on the single-flight `a.forceDone` channel. Changing `recheckForce()` to perform a non-blocking `select` on `<-a.forceDone` (clearing `a.forceUnconfirmed = false` if closed, or returning `agent.ErrCleanupIncomplete` immediately if still open) eliminates the duplicate `StopTimeout` wait on `Stop` after a failed `Start`. In `internal/hub/shutdown.go`, adding optional `AdapterStopTimeout time.Duration` to `ShutdownConfig` (wired to `copilot.DefaultStopTimeout` in `internal/app/shutdown.go`) validates at `NewShutdown` time that `Timeouts.Force >= AdapterStopTimeout` (and defaults `Force` to `max(DefaultShutdownForce, AdapterStopTimeout+2*time.Second)` when `Force == 0`), while leaving `AdapterStopTimeout == 0` unvalidated so existing unit tests that intentionally pass a tiny `Force` (such as `TestShutdownThatCannotConfirmForceStopReportsOrphanRisk`) remain valid.

3. **`4AFE4DA4`, `AEF57AF1`, & `1DCB6108` (`internal/hub`, `internal/transport`, `internal/app`, `internal/tui`)**:
   * **Delivering `server.shutdown` to stale clients (`4AFE4DA4(a)`)**: In `internal/hub/hub.go:714`, `broadcast` skips `c.stale` clients. Special-casing `f.Kind() == KindServerShutdown` in `broadcast` so that for any non-closed client (even if `c.stale` is true or `c.send` is full, evicting one oldest frame via `c.drainOneFrame()` if needed) `server.shutdown` is enqueued via `c.sendFrame(f)` ensures stale clients receive the shutdown reason before `Done()` closes.
   * **Write-completion tracking in `drainAndCloseClients` (`4AFE4DA4(b)` & `AEF57AF1(a)`)**: `drainAndCloseClients` (`internal/hub/shutdown.go:405`) currently checks `len(c.send) == 0`, which becomes true the instant `transport.session.writePump` dequeues the final `server.shutdown` frame from `s.client.Frames()` — before `s.writeFrame(ctx, f.Bytes())` has finished writing it to the WebSocket. Adding atomic `writeAck atomic.Bool` and `inflight atomic.Int64` on `hub.Client` (incremented before sending to `c.send` in `c.sendFrame(f)`, decremented in `c.drainOneFrame()` / `c.drainAllFrames()` and in `c.AckWrite()`, enabled by `transport.newSession` via `client.EnableWriteAck()`, and acknowledged by `writePump` via `s.client.AckWrite()` immediately after `s.writeFrame` returns) allows `c.Drained()` in `queuesEmpty` to wait until the final dequeued frame's socket write has completed with zero race window even when `writePump` receives directly in `select`, while keeping raw `<-c.Frames()` consumers in hub unit tests (`writeAck == false`) zero-overhead.
   * **Pending connects in `reapEmptyBroadcastSet` (`4AFE4DA4(c)`)**: In `internal/hub/permission.go:292`, checking `!h.hasPendingConnect()` (no unabandoned request in `h.pending` and, when `!h.closing`, `len(h.connects) == 0`) before resolving unresolved permissions to `permReasonNoSurface`, calling `h.reapEmptyBroadcastSet()` immediately after `h.serviceHydrations()` in `Hub.Run`, and signalling `trySend(h.membershipWake, struct{}{})` when `Hub.Connect` marks a request `abandoned` prevents an in-flight reconnect from racing the empty-broadcast-set reaper while ensuring abandoned connects never stall `no_surface` reaping. Per design §5.4 and `permission_empty_test.go`, any registered or connecting surface (including observer remotes) counts toward broadcast-set presence.
   * **Concurrent remote drain in `shutdownScenario` and `ctx` propagation in `App.Reissue` (`AEF57AF1(b, c)`)**: Draining `remote` concurrently with `<-r.app.Done()` in `internal/app/e2e_test.go` (`shutdownScenario`) allows the WebSocket peer to echo the close frame during step 5 / `reap` instead of waiting out the 2-second `closeGrace` abort timer. Passing `ctx` into `App.mint(ctx)` and checking `ctx.Err()` before and after locking `a.mintMu` ensures a cancelled `ctx` passed to `App.Reissue(ctx)` / `tuiReissue(ctx)` aborts before revoking or minting credentials.
   * **In-place `(*hub.Client).Rehydrate(ctx)` and resilient `tui.Feed` reconnect/redial (`1DCB6108` & `E9223340(c)`)**: Adding `(*Client).Rehydrate(ctx context.Context) error` (handled on the hub goroutine via `ctlRehydrate`) drains `c.send` via `c.drainAllFrames()` and enqueues a fresh `session.hydrate` snapshot while keeping `c` registered in `h.clients` (`h.tui == c`), eliminating the close-and-redial no-TUI window on feed overflow. Updating `tui.Feed` to call `conn.Rehydrate(dctx)` first on overflow (and exposing `(*Feed).Rehydrate(ctx)` for model-initiated resync recovery), with a bounded retry loop (`RedialRetries`, `RedialBackoff`) when falling back to `Dial` or when `<-conn.Done()` closes without `KindServerShutdown`, prevents both premature `no_surface` permission denials and permanent TUI disconnection on a transient redial error.

4. **`E9223340(a..g)` (`internal/tui`)**:
   * **(a)** Already absorbed in `062-S` (`internal/app/ui.go`).
   * **(b)** Cap live `m.entries` in `tui.Model` at `Options.MaxEntries` (default `hub.DefaultMaxEntries = 1000`), incrementing `m.evicted` when evicting oldest entries, and cache each entry's wrapped string (`wrapped string`, `wrapWidth int`) so streaming deltas only re-wrap the mutated entry in $O(1)$ `lipgloss` wrap calls.
   * **(c)** When `onFrame` sets `m.resync = true` on `hub.ActionRehydrate` or an undecodable `session.hydrate` (unless `f.Kind() == hub.KindServerShutdown`, which sets `m.shutdown = true` without triggering resync), issue a `tea.Cmd` calling `Rehydrater.Rehydrate(ctx)` on `m.ingress` (guarded by `m.resyncRequested`, and emitting `ResyncFailedMsg` on error to clear `m.resyncRequested = false`) to unstick the model.

## Options Evaluated

### Option A: Three Single-Feature Shipments Chained Sequentially (`067-S -> 068-S -> 069-S`)

Decompose the 7 stash entries into three cohesive, single-feature shipments (`n == 1` covering feature per shipment):

1. **Shipment `067-S` (Covering Feature `074-F`: *"Hub fold, publish, and lifecycle hardening"*, declared DAG root under explicit operator P-001 policy exception over `062-S`, with `066-S` `65780da` as code baseline)**: Resolves `2C74C5FC(a, c, d, e, f)`, `550437DB`, and `8769C9A0` across 4 atomic tasks (`074.001-T`..`074.004-T`).
2. **Shipment `068-S` (Covering Feature `075-F`: *"Shutdown broadcast/drain fidelity and in-place hub Client.Rehydrate"*, blocked by `067-S`)**: Resolves `4AFE4DA4`, `AEF57AF1`, `2C74C5FC(b)`, `8769C9A0(c)` app wiring, and the hub half of `1DCB6108` across 4 atomic tasks (`075.001-T`..`075.004-T`).
3. **Shipment `069-S` (Covering Feature `076-F`: *"Resilient TUI reconnect, sanitization, modal anti-spoofing, and viewport hardening"*, blocked by `068-S`)**: Resolves the TUI half of `1DCB6108` and `E9223340(a..g)` across 5 atomic tasks (`076.001-T`..`076.005-T`).

* **Pros**:
  * Strictly satisfies Ship Step 6.1(a1) `S2` (`n == 1` covering feature per shipment).
  * Sequences the hub `Client.Rehydrate` API (`068-S`) ahead of its `internal/tui` consumer (`069-S`), and lands core hub fold/lifecycle fixes (`067-S`) before hub shutdown/drain and reconnect changes (`068-S`).
  * Every task touches `2–3` files, `<= 4` functions, and pairs its production changes with its own red-phase `_test.go` assertions within a single skill domain (`code`) under the 2-hour rule.
* **Cons**:
  * Requires 3 sequential shipment lifecycles in Ship.

### Option B: Two Large Shipments (`067-S` Combining All Hub/Transport/App Changes + `068-S` for TUI)

* **Pros**:
  * One fewer shipment lifecycle (2 instead of 3).
* **Cons**:
  * Combines 8 hub, adapter, transport, and app tasks spanning 6 stash entries into a single 8-task shipment (`067-S`), increasing PR review complexity and coupling fold/operator-lane fixes with WebSocket write-pump drain synchronization and `Client.Rehydrate`.

## Trade-off Comparison

| Criterion | Option A (3 Chained Shipments: `067-S..069-S`) | Option B (2 Shipments: `067-S..068-S`) |
|---|---|---|
| Ship `S2` (`n == 1` feature/shipment) compliance | Full (`074-F`, `075-F`, `076-F`) | Full (`074-F`, `075-F`) |
| PR blast radius & reviewability | Small and cohesive (4–5 tasks per shipment) | High in `067-S` (8 tasks across 4 packages) |
| Architectural layering | Clean (`hub/copilot` -> `hub/transport/app` -> `tui`) | Mixed in `067-S` |
| Alignment with 2-hour rule & Width Isolation | High | Moderate |

## Decision

We select **Option A: Three Single-Feature Shipments Chained Sequentially (`067-S -> 068-S -> 069-S`)**, with the following specific technical decisions:

1. **D-1 (`067-S` DAG Root Declaration under Explicit Operator P-001 Policy Exception over `062-S`, Code Baseline `066-S` `65780da`)**:
   * As established in `063-S..066-S` (`docs/decisions/2026-10-26-intercom-go-mvp-post-062-s-follow-ups-and-root-resolve-deliberation.md`), `062-S` (`6290151`) has `compaction_status: done` and `closure_status: READY_WITH_CONDITIONS` with two open operator-present live-environment conditions (`live-sdk-test-pass` and `tool-approval-routing-live`), while `063-S..066-S` are `READY` and closed on `main` (`7617a00`). Under `.github/policies/workflow-policies.md` P-001 ("unless the operator explicitly overrides P-001"), the operator explicitly selected Capability Set 1 and invoked dark factory mode (`DARK_MODE_ACTIVE`). Therefore, `067-S` is declared a DAG root (`labels: ["dag-root"]`, `predecessor_source: "declared_root"`) under this explicit P-001 policy exception, with `066-S` (`65780da0d83a53182a56460093b80cc132b5d945`) documented as the code baseline, and `067-S -> 068-S -> 069-S` chained via `blocks` dependencies.
2. **D-2 (`067-S` / `074-F`: Hub Fold, Publish, Operator Lanes, Aborted-Idle Permission Resolution, and Adapter Recheck/Timeout Coupling)**:

## Rejected Alternatives

* **Option B (Two Consolidated Shipments)**: Rejected because combining 8 hub/adapter/transport/app tasks into a single shipment creates an unnecessarily large PR blast radius and couples independent failure domains.
* **Local-only prompt echo in `tui.Model.entries` and wall-clock reads inside `Model.View()` (`E9223340(g)`)**: Rejected because `internal/hub/fold.go` folds only SDK events (`message`, `tool`, `error`); synthesizing unsequenced local prompt entries in `m.entries` would vanish on the next `session.hydrate` (breaking live-vs-hydrated parity) and reading `time.Now()` inside `View()` would violate the Elm architecture purity contract documented in `internal/tui/model.go`.

## Risks and Mitigations

* **Risk**: `drainAndCloseClients` waiting on `AckWrite()` could slow down raw `<-c.Frames()` consumers in `internal/hub` unit tests that do not run `transport.session.writePump`.
  * **Mitigation**: Gate `c.Drained()`'s `c.acked.Load() >= c.enqueued.Load()` check on `c.writeAck.Load()`, which is enabled exclusively by `transport.newSession` (`client.EnableWriteAck()`). Raw `hub.Client` consumers in unit tests have `writeAck == false` and continue checking `len(c.send) == 0`.
* **Risk**: Indenting `permission.Summary` by two spaces in `(permission).body()` changes the rendered permission modal layout.
  * **Mitigation**: Update `internal/tui/testdata/modal.golden` in the same atomic unit (`076.002-T`) and verify all `internal/tui` and `internal/app` tests pass.
* **Risk**: Model-initiated `Rehydrate` (`E9223340(c)`) could fire repeatedly if multiple frames arrive while a re-hydrate is already in flight.
  * **Mitigation**: Guard model-initiated re-hydrate dispatch with a `resyncRequested bool` flag on `tui.Model` that is set when the re-hydrate `tea.Cmd` is returned and cleared when a valid `session.hydrate` frame is applied (or when `ResyncFailedMsg` arrives).

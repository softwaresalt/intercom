Capability Set 1 comprises seven deferred-scope-expansion stash entries captured under P-021 C2 during `058-S`, `059-S`, `061-S`, and `065-S`:

2. **`550437DB`** (`high` / `task`): Hub lifecycle wiring gaps for process wiring (7.2): `Hub.Run` ctx cancelled (`SIGINT`) before `Shutdown` stops hub immediately so step 0 returns `ErrStopped`; `Shutdown.Done` never closes if `Start` never called; failed-start cleanup semantics (`Abort` `ErrNotRunning`); `Hub.Run` does not join operator lane workers; operator action `Send`/`Abort` failures only logged (surfaces not told - needs protocol decision); no abort of pending permissions on aborted idle event.

## Research Findings

### Compound Learnings Consulted

* `docs/compound/2026-10-20-process-wiring-credential-panel-and-approval-disarm.md`: Documents the single choke point for disarming armed permission approvals in `onKey` (every key other than `Enter` disarms before any early return), passing initial credentials at `tui.New` construction, and running the hub on a context never cancelled by `SIGINT` before shutdown step 6.
* `docs/compound/2026-10-20-tui-permission-modal-safety-and-linux-test-clock.md`: Documents pinning both `Config.Clock` and `Config.Now` in deterministic hub/TUI tests, keeping `syncModal` synchronized after every mutation of `m.pending`, keeping deny (`n`) available immediately at all times, and separating input fidelity (sent verbatim) from display sanitization (`Sanitize`).
* `docs/compound/2026-10-20-backlogit-cli-pitfalls-and-permission-outcome-lessons.md`: Documents atomic `PermissionOutcome` (`Deliver` vs `Revoke`), running `Agent.Stop` under `context.WithoutCancel` with a hard budget, and keeping delivery-uncertain failed `Send` calls counted in `promptsPending` so a late failure never consumes a later prompt's count.

### Codebase Inspection Findings (Baseline `066-S` / `65780da`)

1. **`2C74C5FC` (`internal/hub/fold.go` & `internal/hub/hub.go`)**:
   * **(a) Duplicate fold error entry on `publish` stub path**: In `internal/hub/hub.go:680-684`, when `publish(kind, payload)` falls back to the `ErrCodeFrameTooLarge` stub, it unconditionally calls `h.fold.ApplyError(ErrCodeFrameTooLarge, msgFrameTooBig)`. When `kind == KindError` (called from `handleDegraded`, `handleEvent` for an unmapped event, or our new operator-action-failure handler), the caller has already called `h.fold.ApplyError(...)`, so the stub path records a duplicate second error entry for the same event. Guarding `if kind != KindError { h.fold.ApplyError(ErrCodeFrameTooLarge, msgFrameTooBig) }` prevents the duplicate entry.
   * **(b) Unswept closed remotes in `admitPending` (also `4AFE4DA4(d)`)**: In `internal/hub/hub.go:920`, `intake` calls `h.admitPending(req)` without calling `h.sweep()`, so remote clients that already closed themselves still count toward `live+remote >= h.pendingLimit()` until `serviceHydrations` runs on the next iteration. Calling `h.sweep()` at the start of `intake` fixes both `2C74C5FC(b)` and `4AFE4DA4(d)`.
   * **(c) `publish` returning `(0, false)` without `markAllStale` or pre-failure cursor invalidation**: In `internal/hub/hub.go:674-677`, if building even the error stub fails, `publish` returns `(0, false)` without calling `h.markAllStale()`. Because `handleEvent` / `handleDegraded` already mutated `h.fold` before calling `publish`, connected clients are out of sync with the fold unless `h.markAllStale()` is executed before returning `(0, false)`. Furthermore, because `replayable` (`internal/hub/hub.go:739-744`) rejects only cursors strictly below `h.degradedSeq` (`p.Seq < h.degradedSeq`), setting `h.degradedSeq = h.seq` would still permit a client whose saved cursor is at the pre-failure head (`p.Seq == h.seq`) to pass `replayable` and receive an empty replay (while `h.seq` remains at the pre-failure head) or only later events (after a subsequent event advances `h.seq`), missing the unsequenced folded update. Setting `h.degradedSeq = seq` (which is `h.seq + 1`, the attempted sequence number) before calling `h.markAllStale()` and returning `(0, false)` guarantees `p.Seq < h.degradedSeq` (`preFailureSeq < preFailureSeq + 1`) is `true` both while `h.seq == preFailureSeq` and after later events advance `h.seq >= seq`, forcing any client reconnecting at `p.Seq <= preFailureSeq` to receive a full `session.hydrate` snapshot carrying the folded update.
   * **(d) `Fold.applyDelta` re-marshalling at cap**: In `internal/hub/fold.go:193`, `if add == "" && !clipped { return }` is false whenever a streaming entry is already at `MaxEntryTextBytes` (`remaining == 0`) and a non-empty delta arrives (`add == ""`, `clipped == true`). Even when `cur.Truncated` is already `true`, `applyDelta` runs `f.replace(i, cur)`, re-marshalling the entire 16 KiB entry on every tiny delta. Changing the early return to `if add == "" && (cur.Truncated || !clipped) { return }` (after setting `f.lastDelta` and `f.anyTrunc`) avoids all redundant marshals once `cur.Truncated` is already set.
   * **(e) `tool.ended` name and truncation parity**: In `internal/hub/fold.go:212-225`, when `applyToolEnded` finds a matching `statusRunning` tool entry, it updates `cur.Status` but ignores `ev.ToolName` and its truncation flag `t2`, whereas `mapEvent` (`internal/hub/envelope.go:275-279`) always bounds `ev.ToolName` with `capIdent` and sets `Truncated: t1 || t2`. Bounding `name, t2 := f.identFlag(ev.ToolName)` up front in `Fold.applyToolEnded` and setting `if cur.Tool == "" && name != "" { cur.Tool = name }` and `cur.Truncated = cur.Truncated || t1 || t2` — together with shipping the matching `if m.entries[i].Tool == "" && name != "" { m.entries[i].Tool = name }` and `m.entries[i].Truncated = m.entries[i].Truncated || p.Truncated` update in `internal/tui/model.go` `applyToolEnded` and a live-versus-hydrated regression test in `internal/tui/model_test.go` inside the exact same task (`074.001-T` in `067-S`) — establishes full fold-vs-live parity without any window between `067-S` and `069-S`.
   * **(f) Drain stale remote buffer on `rehydrate` instead of dropping**: In `internal/hub/hub.go:1099-1102`, `rehydrate(c)` drops `ClientRemote` if `trySend(c.send, f)` finds `c.send` full. Because `rehydrate(c)` is only called for clients marked stale by a hub-wide re-hydrate (`markAllStale` after `SignalDegraded` or an oversize frame stub, or explicit `Client.Rehydrate`), any frames in `c.send` are pre-hydrate frames superseded by the snapshot `f`. Removing the `if c.kind != ClientTUI` drop branch in `rehydrate(c)` so a full `c.send` is drained before sending `f` for both `ClientTUI` and `ClientRemote` (while normal `broadcast` continues to drop `ClientRemote` on overflow) preserves healthy remote clients across degraded-mode re-hydrations.

2. **`550437DB` & `8769C9A0` (`internal/hub` & `internal/agent/copilot`)**:
   * **Process wiring items already handled in `internal/app` (`062-S` / `065-S`)**: `internal/app/assemble.go:220` runs `Hub.Run` on a signal-independent `context.Background()` child cancelled only in `awaitHub()` after step 6; `Shutdown.agentStage` (`internal/hub/shutdown.go:205`) treats `agent.ErrNotRunning` and `agent.ErrStopped` from `Abort` as `noSession = true` (non-error); and `NewShutdown` spawns no goroutine until `Start` is called. We document these caller contracts explicitly in `internal/hub/hub.go` and `internal/hub/shutdown.go`.
   * **Bounded operator lane worker join in `Hub.Run` (`550437DB`)**: `runOperatorLanes(opsCtx)` in `internal/hub/operator.go:53` spawns two worker goroutines without a `sync.WaitGroup`, so `Hub.Run` can return and close `h.done` while a lane worker is still unwinding. Conversely, an unconditional `lanesWG.Wait()` at `Hub.Run` exit would hang `h.Stop()`, `h.Done()`, and `Shutdown.Done()` indefinitely if an in-flight `Agent.Send` or `Agent.Abort` ignores `ctx.Done()`. Adding `lanesWG sync.WaitGroup` on `Hub` (`h.lanesWG.Add(2)` after `if h.cfg.Agent == nil { return }` and `defer h.lanesWG.Done()` in each worker), replacing the `h.promptFailed` send select with `trySend(h.promptFailed, struct{}{})`, and calling a bounded join helper `(*Hub).waitLanes() error` (with `const defaultLaneJoinBudget = 100 * time.Millisecond`, or `min(h.cfg.OperatorActionTimeout, defaultLaneJoinBudget)` when `OperatorActionTimeout > 0`) in `Hub.Run` after `opsCancel()` and `h.shutdown(...)` ensures normal workers are joined before `Hub.Done()` closes while a stalled worker that ignores cancellation times out after `budget`, logs `h.cfg.Logger.Error("hub: operator lane worker ignored cancellation", "err", agent.ErrCleanupIncomplete)`, and returns `apperr.Wrap(apperr.KindInternal, agent.ErrCleanupIncomplete)` from `Hub.Run` while `defer close(h.done)` still executes.
   * **Protocol decision for asynchronous operator `Send`/`Abort` failures (`550437DB`)**: Because `OpPrompt` and `OpAbortTurn` are authorized on the hub goroutine and handed to off-hub lane workers (design §4.1), `Client.Do` returns `ActionResult{Accepted: true}` as soon as the action is queued. When `Agent.Send` or `Agent.Abort` subsequently fails in `callAgent` (and `ctx.Err() == nil`, meaning the failure was not caused by shutdown lane cancellation), logging alone is invisible to remote WebSocket surfaces and to a local TUI whose stderr is discarded on a terminal. We decide to report non-shutdown lane call failures back to the hub select loop via a buffered `actionFailed chan string` (or `opErrs`) channel using non-blocking `trySend` (so a late-returning stalled goroutine never blocks if `Hub.Run` has already exited); the hub goroutine (when `!h.closing`) folds `h.fold.ApplyError(ErrCodeOperatorActionFailed, msg)` and publishes `KindError` (`ErrorPayload{Code: ErrCodeOperatorActionFailed, Message: msg}`, with fixed sanitized messages `"operator prompt send failed"` and `"operator turn abort failed"`, without setting `degradedSeq` or `markAllStale`). Both the TUI and remote clients already render `KindError` entries in the transcript.
   * **Resolving pending permissions and rejecting late aborted-turn asks via turn-scoped ask identity and `permissionBridge` turn cancellation on aborted `agent.idle` (`550437DB`)**: Per design §3.1 SQ-a, `Session.Abort` in the Copilot SDK returns `nil` and emits an aborted idle event (`agent.Event{Kind: agent.KindIdle, Aborted: true}`) without unblocking an already-parked `PermissionHandlerFunc`. Furthermore, `h.ingress` and `h.asks` are independent channels whose relative arrival order is undefined (`internal/agent/agent.go:143-145`): a late ask from the aborted turn can arrive on `h.asks` *after* `KindIdle{Aborted: true}` (`idle-before-ask`) or even enter `permissionBridge.handle` after `abortTurn()` (`abort-before-currentTurn()`), AND a valid ask from the next turn can arrive on `h.asks` *before* the next turn's `KindTurnStart` is dequeued from `h.ingress` (`ask-before-next-turn-start`). An unscoped boolean `turnAborted` latch on the hub cleared only on `KindTurnStart` would falsely reject a valid next-turn permission ask in the `ask-before-next-turn-start` ordering, while clearing `turnID` or replacing `turnStop` inside `abortTurn()` would allow a late callback reaching `currentTurn()` after `abortTurn()` to capture an empty ID and an open channel. Instead, we add `TurnID string` to `agent.PermissionRequest` (`internal/agent/agent.go`), wire turn-scoped generation stamping and retained abort cancellation in `internal/agent/copilot/permission.go` (`permissionBridge`: `mu sync.Mutex`, `turnID string`, `turnGen uint64`, `turnAborted bool`, and `turnStop chan struct{}` initialized in `newPermissionBridge`; `setTurn(id string) string` increments `b.turnGen++`, synthesizes `fmt.Sprintf("turn-%d", b.turnGen)` if `id == ""`, sets `b.turnID`, and when `b.turnAborted || b.turnStop == nil` allocates a fresh open `b.turnStop = make(chan struct{})` and clears `b.turnAborted = false`; `abortTurn() string` synthesizes `b.turnID = fmt.Sprintf("aborted-turn-%d", b.turnGen)` after `b.turnGen++` if `b.turnID == ""`, and when `!b.turnAborted` sets `b.turnAborted = true` and closes `b.turnStop` in place **without** clearing `b.turnID` and **without** replacing `b.turnStop`, retaining the cancelled, non-empty generation until the producer observes the next turn start in `setTurn`; `clearTurn()` clears `b.turnID = ""` when `!b.turnAborted` on normal non-aborted idle; `currentTurn() (string, <-chan struct{})` returns `(b.turnID, b.turnStop)`; and `(*permissionBridge).handle` captures `turnID, turnStop := b.currentTurn()` up front, checks `case <-turnStop: return true` inside `gone()`, stamps `domain.TurnID = turnID`, and selects on `<-turnStop` alongside `<-b.hubDone` and `<-b.stop` both when sending `b.asks <- ask` and when waiting on `<-reply`, closing `ask.Resolved` via `defer close(resolved)` on abort) and `internal/agent/copilot/adapter.go` (`(*Adapter).onEvent` calls `e.TurnID = a.bridge.setTurn(e.TurnID)` on `KindTurnStart` before sending `e` to `a.cfg.Ingress`, calls `abortedID := a.bridge.abortTurn()` and backfills empty `e.TurnID = abortedID` on `KindIdle` with `e.Aborted`, or calls `a.bridge.clearTurn()` on non-aborted `KindIdle`; `(*Adapter).Abort(ctx)` also calls `a.bridge.abortTurn()` when `sess.Abort(ctx)` is invoked), plus `activeTurnID string` and `abortedTurnIDs map[string]struct{}` on `Hub` (`internal/hub/hub.go`). Notice why retaining the closed `turnStop` and non-empty `turnID` in `abortTurn()` until `setTurn` runs on the next turn start closes every gap: (a) any in-flight `b.handle` from the aborted turn (tagged or pre-`KindTurnStart` un-tagged) sees `<-turnStop` close immediately, returns `UserNotAvailable`, and closes `ask.Resolved` so `Hub.handleAsk` discards it via `case <-ask.Resolved:`; (b) any late callback reaching `b.currentTurn()` *after* `abortTurn()` (`abort-before-currentTurn()`) captures the retained non-empty aborted `turnID` and the already-closed `turnStop`, so `gone()` immediately returns `unavailable()` without even enqueuing to `b.asks` (and `domain.TurnID` would also match `h.abortedTurnIDs`); and (c) when the producer observes the next turn's `KindTurnStart` in `onEvent`, `a.bridge.setTurn(e.TurnID)` runs before `a.cfg.Ingress <- e` and opens a fresh `turnStop` with the new `turnID`, so a next-turn ask arriving on `h.asks` before the hub dequeues `KindTurnStart` from `h.ingress` carries the new `turnID` and open `turnStop` and is accepted by `Hub.intakeAsk`. ## Options Evaluated

### Option A: Three Single-Feature Shipments Chained Sequentially (`067-S -> 068-S -> 069-S`)

Decompose the 7 stash entries into three cohesive, single-feature shipments (`n == 1` covering feature per shipment):

1. **Shipment `067-S` (Covering Feature `074-F`: *"Hub fold, publish, and lifecycle hardening"*, declared DAG root under explicit operator P-001 policy exception over `062-S`, with `066-S` `65780da` as code baseline)**: Resolves `2C74C5FC(a, c, d, e, f)`, `550437DB`, and `8769C9A0` across 5 atomic tasks (`074.001-T`..`074.005-T`).
2. **Shipment `068-S` (Covering Feature `075-F`: *"Shutdown broadcast/drain fidelity and in-place hub Client.Rehydrate"*, blocked by `067-S`)**: Resolves `4AFE4DA4`, `AEF57AF1`, `2C74C5FC(b)`, `8769C9A0(c)` app wiring, and the hub half of `1DCB6108` across 4 atomic tasks (`075.001-T`..`075.004-T`).
3. **Shipment `069-S` (Covering Feature `076-F`: *"Resilient TUI reconnect, sanitization, modal anti-spoofing, and viewport hardening"*, blocked by `068-S`)**: Resolves the TUI half of `1DCB6108` and `E9223340(a..g)` across 5 atomic tasks (`076.001-T`..`076.005-T`).

* **Pros**:
  * Strictly satisfies Ship Step 6.1(a1) `S2` (`n == 1` covering feature per shipment).
  * Sequences the hub `Client.Rehydrate` API (`068-S`) ahead of its `internal/tui` consumer (`069-S`), and lands core hub fold/lifecycle fixes (`067-S`) before hub shutdown/drain and reconnect changes (`068-S`).
  * Every task touches `2–3` files, `<= 4` functions, and pairs its production changes with its own red-phase `_test.go` assertions within a single skill domain (`code`) under the 2-hour rule.
* **Cons**:
  * Requires 3 sequential shipment lifecycles in Ship.

### Option B: Two Large Shipments (`067-S` Combining All Hub/Transport/App Changes + `068-S` for TUI)

* **Pros**:
  * One fewer shipment lifecycle (2 instead of 3).
* **Cons**:
  * Combines 8 hub, adapter, transport, and app tasks spanning 6 stash entries into a single 8-task shipment (`067-S`), increasing PR review complexity and coupling fold/operator-lane fixes with WebSocket write-pump drain synchronization and `Client.Rehydrate`.

## Trade-off Comparison

| Criterion | Option A (3 Chained Shipments: `067-S..069-S`) | Option B (2 Shipments: `067-S..068-S`) |
|---|---|---|
| Ship `S2` (`n == 1` feature/shipment) compliance | Full (`074-F`, `075-F`, `076-F`) | Full (`074-F`, `075-F`) |
| PR blast radius & reviewability | Small and cohesive (4–5 tasks per shipment) | High in `067-S` (8 tasks across 4 packages) |
| Architectural layering | Clean (`hub/copilot` -> `hub/transport/app` -> `tui`) | Mixed in `067-S` |
| Alignment with 2-hour rule & Width Isolation | High | Moderate |
